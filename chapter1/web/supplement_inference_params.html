読み始める前に

推論パラメータは、
モデルを一切変えません。

学習済みの重みはそのまま使います。 推論パラメータが変えるのは、モデルが出力した確率分布から 「どのトークンを選ぶか」という最後のステップだけです。

それだけで、同じモデルの出力を堅実にも、大胆にも変えられます。 たとえばコード生成では余計な出力を抑え、アイデア出しでは思い切った表現を引き出せます。 再学習は不要で、学習のための追加コストもかかりません。 推論パラメータは、再学習なしですぐに試せる、低コストな出力の制御手段です。

この仕組みを理解しないまま使うと、 「LLM は毎回答えが変わって使えない」という誤った結論にたどり着きがちです。 このページでは、トークンを選ぶステップで何が起きているのかを見ていきます。

このページで理解すること

  1. LLM の出力が「サンプリング」される仕組み
  2. Temperature が確率分布の形状に与える影響
  3. Top-p / Top-k の動作とユースケース
  4. パラメータの組み合わせ方針

前置き

推論パラメータとは何か

事前学習の補足資料で「LLM は次トークンの確率分布を出力する」と学びました。 推論パラメータは、確率分布が得られた後にどのトークンを実際に選ぶかを制御します。 モデルの重みは変えずに、創造性・多様性・一貫性といった出力の傾向を外側から調整できます。

トークン生成の流れ

Transformer 順伝播
コンテキストを処理し、語彙サイズ分の logit ベクトルを出力します
↓
Temperature 適用
logit を Temperature で割り、分布の形状を変えます
↓
Top-k / Top-p フィルタ
候補を絞り込み、低確率トークンを除外します
↓
サンプリング
残った確率分布から 1 トークンを確率的に選びます
↓ 繰り返す

Greedy 選択との違い

最も確率が高いトークンを常に選ぶ方式を「Greedy デコーディング」と呼びます。 Greedy デコーディングは決定的（同じ入力から同じ出力）ですが、繰り返しや単調な表現が生まれやすくなります。 サンプリングを使うと毎回異なる出力が得られるため、創造的なタスクに向きます。

ハンズオン③ Part 6 では、この流れを model.generate() を使わずに 自分で書きます。Greedy ループは 10 行ほどで実装できます。 Greedy ループに Temperature と Top-p を組み込んだサンプリングの実装例は、付録 E-3 にあります。 LLM の出力が毎回変わるのは、モデルが気まぐれだからではなく、確率分布に従ってサイコロを振っているからです。 この仕組みを、実際に手を動かして確認できます。

Section 1

Temperature は分布の「シャープさ」を制御します

Temperature $T$ は、softmax に渡す前の logit を割ることで確率分布の形状を変えます。 Temperature が低いと分布が鋭く（確実に）、高いと平たく（多様に）なります。

Temperature つき softmax

$$P(x_i) = \frac{\exp(z_i / T)}{\displaystyle\sum_j \exp(z_j / T)}$$
$z_i$ トークン $i$ の logit（Transformer の生スコア）
$T \to 0$ 最大 logit のトークンに確率 1 が集中します（Greedy 選択と等価）
$T = 1$ logit をそのまま softmax にかける標準の動作です
$T \to \infty$ 全トークンの確率が均一になります（ランダム選択と等価）

同じ logit に異なる Temperature を適用した結果

解説動画：Temperature で分布の形が変わる様子（約 28 秒）

logit を Temperature T で割ってから softmax にかけるので、同じ logit でも分布の形が変わります。 T を下げると 1 位の「猫」に確率が集中し（T = 0.3 で 0.96）、T を上げると分布が平らになります（T = 2.0 で 0.38）。 logit は Section 1 の図と同じ [3.0, 2.0, 1.5, 0.8, 0.2] です。

Temperature の推奨設定

値の目安 特性 適したユースケース
0.0 – 0.3 確実・再現性高 コード生成・ファクト抽出・分類
0.7 – 1.0 バランス型 一般的な会話・要約・翻訳
1.0 – 1.5 多様・創造的 創作・ブレインストーミング・詩

Section 2

Top-p と Top-k は候補を絞り込みます

Temperature が分布の形を変えるのに対し、Top-p と Top-k は サンプリングの候補集合そのものを絞り込むフィルタです。 低確率の「外れ値トークン」が選ばれるのを防ぎ、出力品質を安定させます。

Top-k サンプリング

確率の高い上位 $k$ 個のトークンだけを残し、それ以外を除外します。 残ったトークンの確率を再正規化してから、サンプリングします。

特徴: 候補数は常に一定です。分布が広い場合でも、低確率トークンが混入しにくくなります。

Top-p サンプリング（Nucleus）

確率の高いトークンから順に確率を足し合わせ、累積確率が初めて $p$ 以上になったトークンまでを残し、それより後のトークンを除外します。下の図では確率が 0.50, 0.25, 0.17, … なので、累積確率は 0.50 → 0.75 → 0.92 と増えます。3 位で 0.9 以上になるため、1〜3 位が残ります。

特徴: 候補数は分布の形に応じて変わります。モデルの確信度が高いときは、少数の候補から選びます。

解説動画：Top-p で候補を絞ってから選ぶ（約 28 秒）

確率の高い順に累積確率を足し、初めて p = 0.9 以上になった 3 位までを残します。 4 位以降を除外し、残った 3 つを合計 0.92 で割って再正規化してから、その中から確率に比例して 1 つ選びます。 最後に、候補数が常に一定の Top-k（k = 3）と比べます。

Top-p と Top-k の使い分け

一般的には Top-p（Nucleus Sampling）が推奨されます。 Top-p は確率分布の形状に応じて候補数を自動で調整するため、 「鋭い分布のときは決定的に、広い分布のときは創造的に」振る舞います。 Top-k は、候補数を一定に保ちたい場合に使います。

Section 3

その他の主要パラメータ

max_new_tokens 生成する最大トークン数

生成を打ち切るトークン数の上限です。小さすぎると文章が途中で切れ、 大きすぎると不要な繰り返しや中身のない文が生まれやすくなります。 目安として、要約では 128〜256、コードでは 512〜2048 に設定します。

repetition_penalty 繰り返しへのペナルティ

すでに系列に出現したトークン（プロンプトと生成済みの部分の両方）の logit を小さくして、同じ表現の繰り返しを抑えます。正の logit は $r$ で割り、負の logit は $r$ を掛けます。$r > 1$ なら、どちらも値が小さくなり、選ばれにくくなります。

$$z'_i = \begin{cases} z_i / r & \text{既出トークンで } z_i \ge 0 \\ z_i \cdot r & \text{既出トークンで } z_i \lt 0 \\ z_i & \text{それ以外} \end{cases}$$

設定値の目安は $r = 1.0$（変化なし）〜 $r = 1.3$（強めのペナルティ）です。大きくしすぎると文が不自然になります。

do_sample サンプリングの有効化

False の場合は Greedy デコーディングになります。 transformers 自体のデフォルトは False ですが、モデルに同梱された generation_config.json がデフォルトを上書きすることがあります。 たとえば Llama-3.2-1B-Instruct は do_sample=true、temperature=0.6、top_p=0.9 を設定しているため、何も指定しなくてもサンプリングになります。 確実に Greedy デコーディングにしたい場合は、 do_sample=False を明示します。 Temperature / Top-p / Top-k を有効にするには do_sample=True が必要です。

use_cache KV キャッシュの有効化

生成は 1 トークンずつ進むため、素朴に実装すると 毎ステップで過去すべてのトークンの K・V を計算し直すことになります。 過去の K・V を保存して再利用する仕組みが KV キャッシュです。 True（デフォルト）のままで構いません。 ただし実運用では、長いコンテキストや大きなバッチで推論すると、KV キャッシュがメモリ使用量の大きな割合を占め、モデルの重みより大きくなることもある点に注意が必要です。短いプロンプトを 1 件ずつ処理する場合は、モデルの重みがメモリの大部分を占めます。 KV キャッシュはプロンプトが長いほど効果が大きく、ハンズオン③の付録 E-2 では 481 トークンのプロンプトで約 2.4 倍の高速化を実測します。

HuggingFace generate() の典型的な設定例 
from transformers import AutoTokenizer, AutoModelForCausalLM
import torch

model_name = "meta-llama/Llama-3.2-1B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    dtype=torch.float16,   # 新しい transformers では dtype=、古いバージョンでは torch_dtype=
    device_map="auto",
)
model.eval()

prompt = "深層学習とは何か、一言で説明してください。"
inputs = tokenizer(prompt, return_tensors="pt").to(model.device)

# ── 創造的なタスク向け設定 ──────────────────────────────
outputs_creative = model.generate(
    **inputs,
    max_new_tokens=200,
    do_sample=True,
    temperature=1.1,       # 高温 → 多様な表現
    top_p=0.92,            # 上位 92% の累積確率から選択
    repetition_penalty=1.1,
)

# ── 正確さが求められるタスク向け設定 ─────────────────────
outputs_factual = model.generate(
    **inputs,
    max_new_tokens=200,
    do_sample=True,
    temperature=0.2,       # 低温 → 確実・再現性高
    top_p=0.9,
    repetition_penalty=1.0,
)

print(tokenizer.decode(outputs_creative[0], skip_special_tokens=True))
print(tokenizer.decode(outputs_factual[0],  skip_special_tokens=True))

Section 4

パラメータの組み合わせ方針

パラメータは互いに影響し合うため、「Temperature だけ下げれば品質が上がる」とは限りません。 タスクの性質に合わせてセットで調整するのが基本です。

タスク別推奨パラメータセット

タスク Temperature Top-p rep. penalty
コード生成・バグ修正 0.1 – 0.3 0.90 1.0
ファクト抽出・要約 0.2 – 0.5 0.90 1.1
一般的な Q&A・会話 0.7 – 0.9 0.92 1.1
創作・ブレスト 1.0 – 1.3 0.95 1.15
多様な候補を列挙 1.2 – 1.5 0.98 1.2

※ 最適値はモデルによって異なります。ハンズオン③ Part 7 で出力の変化を観察し、付録 F で TTR（Type-Token Ratio）・Jaccard 類似度による定量評価まで行います。

よくある失敗パターン

  • Temperature を上げすぎる（目安として 1.5 を超える）と、意味をなさないトークン列が生成されやすくなります
  • Top-p と Top-k を両方設定すると、制約が二重になり、候補が極端に絞られる場合があります。transformers では top_k の既定値が 50 のため、top_p だけを指定しても Top-k（k = 50）が同時に効きます。Top-k を無効にするには top_k=0 を指定します
  • do_sample=False のまま Temperature を変えると、Greedy デコーディングのため Temperature の設定は無視されます
