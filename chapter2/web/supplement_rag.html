RAG パイプラインの構成要素

知識を外部DBに持たせて LLM の回答を強化する仕組み

1

RAG とは何か

Retrieval-Augmented Generation (RAG) は、質問に答える前に関連ドキュメントを検索して コンテキストとして LLM に渡す手法です。 コンテキストとは、LLM に一緒に読ませる参考情報のことです。試験でいうと、暗記だけで答えるのではなく、持ち込み資料の該当ページを開いてから答えるイメージです。 SFT でモデルに知識を「焼き込む」のではなく、知識を外部データベースに置いておき、必要に応じて検索します。

RAG の処理フロー

1

ドキュメントの分割（チャンキング）

長い文書をテキストチャンクに分割します。
ここでチャンクとは「検索しやすい短いかたまり」です。
たとえば10ページの資料を、段落ごとのメモカードに分けるイメージです。
このチャンクサイズは検索精度に影響します。

2

エンベッディング（ベクトル化）

各チャンクを埋め込みモデルで高次元ベクトルに変換し、ベクトルDBに格納します。
ベクトル化とは、文章の意味を数値のリストで表すことです。たとえば「犬」と「子犬」は近い数値、「犬」と「契約書」は遠い数値になります。

3

類似検索（Retrieval）

ユーザーの質問をベクトル化し、コサイン類似度で上位 k 件のチャンクを取得します。
パラメータとして使用するtop-k の k は「似ている資料を何件持ってくるか」を表します。
k=3 なら、最も近いメモカードを3枚取り出すイメージです。

4

コンテキスト付き生成（Generation）

取得したチャンクを「参考文書」としてプロンプトに埋め込み、LLM に回答させる。

2

チャンクサイズの影響

チャンクサイズは RAG の精度に直結する最重要パラメータです。短すぎると情報が途中で切れ、長すぎると関係ない説明まで混ざります。ハンズオンでは 3 通りを比較します。 token は文字数と完全には一致しないため、以下の情報量はあくまで目安です。

チャンクサイズ情報量の目安メリットデメリット向いているケース
256 tokenX(Twitter)の短い投稿数個分、FAQ 1〜2項目程度ピンポイントで関連箇所を取れる文脈が途切れやすいFAQ・短い定義文
512 token短いブログ節や、技術説明の小見出し1つ程度精度とコンテキスト量のバランス—一般的な技術文書
1024 token長めの節や、ドキュメント1ページ弱程度段落全体の文脈を保てるノイズが増えやすい論文・長い説明文

チャンクに オーバーラップ（overlap=50〜100 token）を設定すると、 チャンク境界で情報が切れる問題を緩和できます。オーバーラップとは、隣り合うチャンクに同じ文を少し重ねて入れることです。ページをコピーするときに、前後の数行も一緒に写して文脈を残すイメージです。

LangChain + ChromaDB の実装パターン

from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_community.embeddings import HuggingFaceEmbeddings
from langchain_community.vectorstores import Chroma
from langchain_community.document_loaders import TextLoader

# 1. ドキュメント読み込み
loader = TextLoader("./docs/sample.txt", encoding="utf-8")
documents = loader.load()

# 2. チャンキング
splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,       # チャンクサイズ (token 数の近似)
    chunk_overlap=50,     # 前後チャンクとの重複量
    length_function=len,
)
chunks = splitter.split_documents(documents)
print(f"チャンク数: {len(chunks)}")

# 3. エンベッディング + ベクトルDB作成
embeddings = HuggingFaceEmbeddings(
    model_name="sentence-transformers/all-MiniLM-L6-v2",
    model_kwargs={"device": "cpu"},
)
vectorstore = Chroma.from_documents(chunks, embeddings)

# 4. 類似検索（top-k=3）
query = "機械学習における過学習とは何ですか？"
results = vectorstore.similarity_search(query, k=3)
for i, doc in enumerate(results):
    print(f"--- 検索結果 {i+1} ---")
    print(doc.page_content[:200])

SFT vs RAG の使い分け

観点SFTRAG
知識の更新頻度低い（再学習が必要）高い（DBを更新するだけ）
推論コスト低い（モデルに内包）高い（検索 + 生成）
幻覚（hallucination）抑制しにくい参照元を明示できる
応答スタイルの変更得意苦手
ドメイン知識の深さ中程度（データ量に依存）ドキュメントの質に依存

実務での組み合わせ
SFT で応答形式・スタイルを固め、RAG で最新の知識を補完するという SFT + RAG のハイブリッドが実務では最もよく使われるパターンです。 たとえば「必ず結論から箇条書きで答える」部分は SFT、「最新の社内規程を参照する」部分は RAG に任せます。
