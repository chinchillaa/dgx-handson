# テンプレートの読み心地を確認する例

既存の評価材料を、新しいテンプレートに沿って編集した例です。
実プロジェクトの調査結果やテスト実績ではありません。材料にないコードや実行結果は補っていません。

## レビュー指摘を段落でつなぎます

材料は `cases/review.md` です。1 件の指摘なので、一覧表を置かずに根拠から修正へ進みます。

### [Critical] 決済失敗を画面が成功として扱います

決済が失敗しても画面は成功として表示するため、マージを保留してください。
画面が決済失敗を表示できるように修正してください。

`apps/api/src/handlers/payment.ts:120-138` は、決済 API の例外を捕捉して `null` を返しています。
この処理で失敗を隠すため、画面は成功として扱います。返金処理の記録も残りません。

画面が失敗を判別できるように、決済処理から呼び出し元へ失敗を伝えてください。
同じ書き方がある `refund.ts:88` も確認します。返金の失敗も呼び出し元へ伝える修正が必要です。

失敗した注文を追跡できるように、ログには `orderId` を残してください。

決済側は、リポジトリルートで次のテストを実行して確認します。実行結果は未確認です。

```bash
pnpm --filter @example/api test src/handlers/payment.test.ts
```

返金側のテストと画面表示を確認する手順は、対象コードを調べて特定してください。

- [ ] 決済失敗時に画面が失敗を表示します。
- [ ] 返金失敗時に呼び出し元で失敗を判別できます。
- [ ] 失敗した注文の `orderId` をログで確認できます。

## 技術提案を判断の順序で組み立てます

材料は `cases/design-doc.md` です。本実装の採用前に、要件と移行時の挙動を検証する提案に整理します。

### 通知処理の分割と、BullMQ による再試行を検証します

編集競合を減らすための通知処理の分割と、失敗した通知を再試行する仕組みの検証を提案します。
今回は、この検証への着手を承認してください。
BullMQ は送信待ちの処理を管理するジョブキューです。`apps/worker` に開発環境があり、検証に利用できます。

本実装の採用は、送信の遅延、二重送信の防止、Redis の運用体制を確認してから判断します。

#### 送信処理を種類ごとに分け、編集箇所の集中を減らします

`apps/api/src/notify.ts` は 1,400 行あり、メール、Slack、Web Push の送信処理がまとまっています。
送信先を追加するたびに同じファイルを変更するため、提供された材料では月に約 3 回の競合が報告されています。

送信処理を種類ごとに分け、送信先を追加するときの変更箇所を分散させる方針です。
通知の文面を管理する処理も同じファイルにありますが、今回の変更対象には含めません。

- [ ] 送信先を追加する変更例で、既存の送信処理への変更箇所を比較し、分割によって編集箇所を分散できるか確認します。

#### 切り出した送信処理を BullMQ で再試行します

現在は通知の送信に失敗すると、そのまま再試行しません。
BullMQ に送信処理を登録し、失敗した処理を再試行する構成を検証します。

種類ごとに切り出した送信処理を BullMQ から呼び出す構成にします。
処理の分割は編集箇所の集中を減らすため、BullMQ の導入は再試行を管理するための変更です。

- [ ] 送信を意図的に失敗させた検証で、再試行によって通知を送れることを確認します。

#### BullMQ の採用には Redis の運用担当が必要です

| 評価軸 | BullMQ（推奨） | Cloud Tasks |
|---|---|---|
| 開発環境 | `apps/worker` の既存環境を利用できる | 材料ではローカル開発にエミュレータが必要とされている |
| 運用負担 | Redis の運用が必要になる | 基盤の管理をサービスへ任せられる |

Redis を扱える人は 2 人です。運用を引き受けられるか、この 2 人に確認します。
担当を確保できない場合は、Cloud Tasks での検証を検討します。

- [ ] Redis の運用担当と担当範囲を決め、検証後に本実装の採用を判断できる状態にします。

#### Web Push の許容遅延が分からないため、性能はまだ判定できません

Web Push は遅延の要件が厳しいとの報告がありますが、決定者と許容値は未確認です。
許容値が分からないと、キューで送信を待たせても問題ないか判断できません。
計測の前に、要件の決定者へ許容値を確認します。

負荷条件は、日次の送信量を出発点に決めます。日次の件数だけでは、送信が集中する時間帯の負荷は分かりません。

| 送信先 | 日次の送信量 |
|---|---|
| メール | 12,000 通 |
| Slack | 3,000 件 |
| Web Push | 45,000 件 |

- [ ] Web Push の要件の決定者と、許容遅延を確認します。
- [ ] 合意した負荷条件で遅延を計測し、許容値と比較した結果を記録します。

許容値を超える場合は送信方式を見直し、BullMQ の採用判断を保留します。

#### 送信経路の切り替え時に、二重送信を防ぎます

移行中は新旧の送信経路が並走するため、同じ通知を両方の経路が送る可能性があります。
`apps/api/src/notify.ts` の呼び出し元は 23 箇所あります。
各呼び出し元が使う送信経路を調べ、経路を切り替えたときの送信件数を確認します。
二重送信を防げない場合は並走を採用せず、切り替え方法を見直します。

- [ ] 呼び出し元 23 箇所について、切り替え時の送信経路を確認します。
- [ ] 新旧の経路を切り替える検証で、同じ通知を二重に送らないことを確認します。

## 読み直すときの確認点

- 冒頭だけで、読者が取るべき行動を理解できますか。
- 見出しだけで、何が分かり、何が判断を止めているかを理解できますか。
- 数値は、それを使う判断の近くにありますか。
- 原因と結果を、離れた箇条書きから組み立て直さずに読めますか。
- 期待する画面や出力を読んでから、内部の処理を追えますか。
- 確認項目の理由を、同じ節の中で理解できますか。
- 表は比較に、段落は理由の説明に使えていますか。
- 根拠、未確認事項、提案を区別できますか。
- 材料の数値・識別子・制約を保ち、実績を作らずに書けていますか。

この例は編集者による確認用であり、独立した生成比較の結果ではありません。
読み心地の改善は、例を読んだ利用者の評価で確認します。
